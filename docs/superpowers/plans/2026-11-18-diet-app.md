# Diet App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the diet app described in `docs/idea.md` (week meal plan, meals and ingredients
databases, shared shopping list) as a SvelteKit app backed by MySQL.

**Architecture:** SvelteKit (adapter-node) with `load` functions and form actions for most pages.
The shopping list uses a JSON API with client `$state` and polling. Business rules (nutrition, dates,
shopping-list building and merging, auth tokens, cleanup selection) live in pure, unit-tested modules
in `src/lib`. Database access goes through thin Drizzle repository modules in
`src/lib/server/repositories`.

**Tech Stack:** TypeScript strict, SvelteKit 2 + Svelte 5 runes, Drizzle ORM (`mysql2`), MySQL 8,
valibot, sharp, Vitest (node + browser projects), oxlint, Prettier, pnpm 10, Node 22.

**Spec:** `docs/superpowers/specs/2026-11-18-diet-app-design.md` (technical design) and
`docs/idea.md` (product behavior). Read both before starting any task.

## Global Constraints

- TypeScript `strict`, target ES2022. Package manager pnpm 10 (pinned in the `packageManager` field). `engines.node: ">=22"`.
- Naming: shared constants are camelCase (`users`, `mealTypes`, `sessionTtlMs`), never SCREAMING_CASE. Only external names keep their own casing (env vars like `DATABASE_URL`, MySQL error codes like `ER_DUP_ENTRY`).
- Svelte 5 runes only (`$state`, `$derived`, `$props`, `$effect`). No legacy `export let` or stores for new code.
- All UI text is Polish and comes from `src/lib/i18n/pl.ts`. Never hardcode UI text in components. Code, comments and docs are in English.
- Users, categories, meal types and units come only from `src/lib/config/*`. Never assume there are exactly two users.
- The database stores config keys as `varchar`, not MySQL `ENUM`.
- Nutrition is never stored. It is always calculated with `src/lib/nutrition.ts`.
- Amounts: `g`/`ml` are per 100, `pcs` is per 1 piece. Display kcal as an integer and macros to 1 decimal. Display shopping amounts for `g`/`ml` as integers and `pcs` to at most 1 decimal, using `Intl.NumberFormat('pl-PL')`.
- Drizzle `DECIMAL` values become `number` in repositories, never in components.
- Read environment variables via `$env/dynamic/private`: `DATABASE_URL`, `APP_PASSWORD`, `SESSION_SECRET`, `PHOTOS_DIR`, `TZ=Europe/Warsaw`, plus adapter-node `ORIGIN`, `PORT`, `ADDRESS_HEADER` and `BODY_SIZE_LIMIT=10M`.
- An ingredient's unit is immutable after creation. Shopping-list items cannot be deleted individually.
- UI components come from the project's own library in `src/lib/components/ui`, styled with `src/lib/styles/base.css` variables and utilities. No UI framework.
- Screens follow the spec's **UI design** section (tokens, rules, screen notes) and the approved mockups linked there. Components use the CSS variables, never raw hex; per-person colors come from `users` config. Touch targets ≥ 44px; inputs use 16px text; icons are inline stroke SVG components in `src/lib/components/icons/`.
- Each task ends with these all passing: `pnpm lint`, `pnpm format:check`, `pnpm check`, `pnpm test`.

## Review Focus

1. **Polish decimal input.** A user types `1,5` (comma) for an amount or a nutrition value. It must be accepted as `1.5`, not rejected or read as `15`. Covered by a test in Task 5.
2. **Weeks that cross a month, year or DST boundary.** For example, `2026-10-25` is a DST change, and `2026-12-31` spans into 2027. The week bar must show the correct seven dates, Monday first. Covered by a test in Task 3.
3. **All users excluded from a planned meal.** That meal must add nothing to the shopping list. Never create an item with amount 0. Covered by a test in Task 14.
4. **A refresh response that arrives after a local change.** If the user ticks an item while a poll is in flight, the poll's older data must not flip it back. Covered by a test in Task 15.
5. **Duplicate meal name differing only in case.** For example, `Owsianka` and `owsianka`. The duplicate must produce a form error on the name field, not a 500. Covered by a test in Task 7.

- [ ] **Step 3: Implement `auth.ts`, `handle`, and the login and logout routes**
