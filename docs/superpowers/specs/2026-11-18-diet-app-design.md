# Diet app: technical design

Date: 2026-11-18
Product spec: [`docs/idea.md`](../../idea.md) (source of truth for behavior).
Tech stack: [`AGENTS.md`](../../../AGENTS.md).

This document describes how to build what `idea.md` describes. It does not repeat product rules
unless the implementation depends on them.

## Intent

A small, self-hosted web app for two people to plan a week of meals, keep a meal and ingredient
database, and build a shared shopping list. It runs on the author's VPS and is used mostly on phones.
The priorities are correct numbers (nutrition always reflects the current ingredient values and
multipliers), low maintenance, and simple code.

## Goals, non-goals, anti-goals

- **Goals:** everything in `idea.md`; nutrition always correct after any ingredient edit; fast on mobile;
  easy to change users, categories and meal types in code.
- **Non-goals:** per-user accounts, offline mode, real-time push (WebSockets), E2E tests, settings UI,
  nutrition goals.
- **Anti-goals:** stored or cached nutrition totals that can go stale; a page reload or lost input
  while the shopping list refreshes; a heavy client-side state layer for pages that work fine as forms.

## Approaches considered

**Nutrition (decided: calculated on the fly).** Meals and planned meals store only ingredient
references and amounts. kcal and macros are calculated on every read from the current ingredient
values and the current user multipliers. Storing totals was rejected: every ingredient edit would
have to recalculate all meals and planned days, and the stored numbers could go stale. With two users
the data volume is tiny, so calculating on read costs nothing.

**Planned meals (decided: copies that point at shared ingredients).** Adding a meal to a day copies
the meal's name, photo, preparation and ingredient list into plan tables. The copied ingredient rows
reference the same `ingredients` table. Editing a day changes only its copy, ingredient edits reach
every copy, and deleting a meal from the database leaves the plan intact.

**Server communication (decided: form actions + a JSON API for the shopping list).**

1. *Chosen:* SvelteKit `load` functions plus form actions (`use:enhance`) for most pages. The shopping
   list (mark as done or undone, change an amount, add a manual item, periodic refresh) uses JSON
   endpoints called with `fetch`, with the list kept in client `$state`. A JSON endpoint also serves
   paged results to the meal picker as the user scrolls.
2. *Rejected:* a JSON API for everything. It means more client code, and you redo the validation and
   error handling that form actions provide.
3. *Rejected:* SvelteKit remote functions. They have the least boilerplate, but they were still
   experimental when checked.

## Configuration in code

All under `src/lib/config/`. Each list is a `const` array of string keys. The database stores the keys
as `varchar`, not as MySQL `ENUM`, so adding a value never needs a migration. Polish labels come from
`src/lib/i18n/pl.ts`.

- `users.ts`: `users = [{ key: 'user1', name: 'Osoba 1', multiplier: 1.0, color: '#2457A6', tint: '#F3F6FB' },
  { key: 'user2', name: 'Osoba 2', multiplier: 1.0, color: '#B0531A', tint: '#FBF4EF' }]`. Names are
  placeholders. `color` marks the person everywhere in the UI (dots, column headers); `tint` is the
  background of their amount cells. Keys are stable identifiers stored in the database (exclusions).
  Code always iterates `users` and never assumes there are two.
- `categories.ts`: ingredient categories (`vegetables`, `fruit`, `dairy`, `meat`, `fish`, `grains`, …).
- `meal-types.ts`: `breakfast`, `second_breakfast`, `lunch`, `dinner`, `snack`.
- `units.ts`: `g`, `ml`, `pcs`. Nutrition is entered per 100 g, per 100 ml or per 1 piece.

Validation uses `v.picklist(...)` built from these arrays.

## Database (MySQL 8 (confirmed, not MariaDB), Drizzle)

Schema in `src/lib/server/db/schema.ts`. Migrations go in `drizzle/`, are generated by `drizzle-kit`
and are reviewed before applying. Character set `utf8mb4`. Name columns use
`utf8mb4_pl_0900_ai_ci`, so sorting follows Polish rules and search and uniqueness ignore case.
Numeric amounts use `DECIMAL`. Dates use `DATE` (Drizzle `mode: 'string'`, `YYYY-MM-DD`).

```
ingredients
  id            int PK auto
  name          varchar(120) not null
  unit          varchar(8)  not null          -- g | ml | pcs
  category      varchar(32) not null
  kcal          decimal(7,2) not null         -- per 100 g / 100 ml / 1 pc
  protein       decimal(7,2) not null
  fat           decimal(7,2) not null
  carbs         decimal(7,2) not null
  hidden_at     datetime null                 -- "deleted" = hidden
  created_at, updated_at

meals
  id            int PK auto
  name          varchar(120) not null UNIQUE
  photo_path    varchar(64) null              -- file name in PHOTOS_DIR
  preparation   text null
  created_at, updated_at

meal_types         (meal_id FK→meals ON DELETE CASCADE, type varchar(32)) PK(meal_id, type)

meal_ingredients
  id, meal_id FK→meals ON DELETE CASCADE,
  ingredient_id FK→ingredients ON DELETE RESTRICT,
  amount decimal(8,2) not null, position int not null

plan_meals
  id            int PK auto
  date          date not null
  position      int not null                  -- order within the day
  source_meal_id int null FK→meals ON DELETE SET NULL
  name          varchar(120) not null         -- copied, editable per day
  photo_path    varchar(64) null              -- copied
  preparation   text null                     -- copied
  created_at
  INDEX (date, position)

plan_meal_ingredients
  id, plan_meal_id FK→plan_meals ON DELETE CASCADE,
  ingredient_id FK→ingredients ON DELETE RESTRICT,
  amount decimal(8,2) not null, position int not null

plan_meal_exclusions (plan_meal_id FK→plan_meals ON DELETE CASCADE, user_key varchar(32))
  PK(plan_meal_id, user_key)

shopping_list_items                           -- one list, so no list table
  id            int PK auto
  ingredient_id int null FK→ingredients       -- null = manual item
  name          varchar(120) null             -- manual items only
  unit          varchar(8) null               -- manual items only, optional
  amount        decimal(10,2) null            -- optional for manual items
  done_at       datetime null
  created_at
```

Notes:
- An ingredient's `unit` is set on creation and can never be changed (decided). Amounts are bare
  numbers interpreted in the ingredient's unit, so changing it would silently corrupt every meal,
  plan and shopping-list amount. The edit form shows the unit read-only, and the edit action and its
  valibot schema do not accept `unit`. To use a different unit, the user creates another ingredient.
- Ingredients are never hard-deleted, so `RESTRICT` foreign keys are safe. Hidden ingredients are
  excluded from search, the list page and pickers, but still join normally everywhere else.
- Ingredient names are not unique in the database. The app rejects a new or renamed ingredient whose
  name matches a visible ingredient (my call: this keeps pickers unambiguous and still allows reusing a
  hidden one's name).
- Meal deletion is a hard delete. `meal_types` and `meal_ingredients` cascade, and `plan_meals` keep
  their copy (`source_meal_id` becomes null).
- For plan items, the shopping list's unit, name and category always come from the joined ingredient.

## Nutrition calculation

Pure functions in `src/lib/nutrition.ts`, shared by server and client and unit-tested:

- `itemNutrition(ingredient, amount)`: factor = `amount / 100` for `g` and `ml`, `amount` for `pcs`.
  Multiply kcal, protein, fat and carbs by the factor.
- `sumNutrition(items)`: base nutrition of a meal (one average portion).
- `forUser(nutrition, multiplier)`: per-user values.
- `planMealPerUser(planMeal, users)`: per-user values, with `null` for excluded users.
- `dayTotals(planMeals, users)`: per-user sums for the day, skipping exclusions.

Calculate unrounded and round only for display: kcal to an integer, macros to 1 decimal. Use
`Intl.NumberFormat('pl-PL')`. Drizzle returns `DECIMAL` as a string; convert to `number` in the data
layer, never in components.

## Routes

```

/logout                         POST action; clears cookie
/                               redirect → /plan
/plan?date=YYYY-MM-DD           week bar + day view (default date = today)
/plan/[planMealId]              cooking view: ingredients per user + preparation; keeps screen on
/plan/[planMealId]/edit         edit this day's copy; actions: save, saveAsRecipe
/meals?q=&type=                 meals database (scroll-loaded list)
/meals/new                      create meal
/meals/[id]                     meal details: photo, ingredients, per-user nutrition, preparation
/meals/[id]/edit                edit meal; action: delete
/ingredients?q=                 ingredients list with search
/ingredients/new
/ingredients/[id]/edit          edit; action: hide
/shopping-list                  list page (client state + JSON API)
/shopping-list/from-plan        pick days/meals → create (merge/replace)
/photos/[file]                  serves files from PHOTOS_DIR

JSON:
GET    /api/meals?q=&type=&cursor=          picker / meals list pages (30 per page)
GET    /api/ingredients?q=                  ingredient picker search (top 20, visible only)
GET    /api/shopping-list                   full list
POST   /api/shopping-list/items             add an item: manual { name, amount?, unit? } or { ingredientId, amount? }
PATCH  /api/shopping-list/items/[id]        { done?: boolean, amount?: number | null }
```

### Plan page

- `load` resolves the Monday–Sunday week that contains `date`. It returns that week's planned meals,
  with ingredients and exclusions, in one query set. Day buttons, the week arrows and **Today** are
  links that change `?date=`.
- "Today" is computed on the server in `Europe/Warsaw` (`TZ` env var).
- Actions on `/plan`: `add` (date, mealId → copy, position = last + 1), `replace` (planMealId, mealId →
  overwrite the copy's name, photo, preparation and ingredients; position and exclusions stay),
  `remove` (the UI asks for confirmation first), `toggleExclusion` (planMealId, userKey), `reorder` (date, ordered planMealIds).
- Drag to reorder needs touch support. The builder picks the library (for example
  `svelte-dnd-action`, if it supports Svelte 5) or implements it with pointer events. On drop, the UI
  posts to `?/reorder` and does not reload.
- The meal picker is one `MealPicker` component used for add and replace (in a dialog) and on
  `/meals`. Search and type filters are debounced, and it loads more results from `/api/meals` when
  the user scrolls near the end of the list (keyset pagination on `(name, id)`).

### Edit planned meal

Same form component as a meal (`MealForm`) without photo upload or types. **Save** rewrites the
copy's ingredient rows. **Save as new recipe** inserts a new `meals` row (name must be unique, and the
user picks the types) from the edited copy, reusing the copy's photo file.

### Meal forms

`MealForm` contains the name, types, an optional photo, the ingredients and the preparation.
Ingredients are added with an ingredient search (`/api/ingredients`). Each row shows the amount field
with the ingredient's unit label next to it ("Jajka [ 2 ] szt."). The form submits as
`multipart/form-data`, and the ingredient rows are serialized as indexed fields or one JSON field
(builder's choice), then validated with valibot.

## Shopping list

Server logic in `src/lib/server/shopping-list.ts`. The aggregation and merge parts are pure
functions, unit-tested:

- **Build from plan:** for each selected planned meal and each of its ingredients, add
  `amount × sum of multipliers of non-excluded users`, grouped by `ingredient_id`.
- **Create** (form action on `/shopping-list/from-plan`, in a transaction):
  - If no item is not-done: delete all items and insert the built ones.
  - Otherwise, the page asks (dialog) whether to **merge** or **replace** before it submits
    `mode=merge|replace`. The server checks this again and returns a `fail` if `mode` is missing
    while undone items exist.
  - `replace`: delete all, insert built.
  - `merge`: for each built ingredient, if a not-done, non-manual item with the same `ingredient_id`
    exists, add to its amount; otherwise insert. Manual and done items are left untouched.
- The `/shopping-list/from-plan` page shows days from today to the last planned day, each with its
  meals as checkboxes, all checked by default.

- Items can't be deleted one by one (decided). They can only be marked done or undone. The list is
  cleared only when a new list is created from the plan (`replace`, or building directly when nothing
  is undone). There is no delete endpoint and no "clear" button.

### List page (client)

- `load` returns the initial items. After that, the list lives in `$state` and changes through the
  JSON API:
  - Toggling done or undone, and editing an amount, update the UI optimistically and then
    `PATCH`. On failure, roll back and show an error.
  - Adding an item calls `POST` and inserts (or replaces) the returned row.
  - Quick-add suggestions: typing in the name field (debounced 300 ms) shows up to 6 visible ingredients
    from `GET /api/ingredients?q=`, each with its category label and unit. Picking one links the row
    to that ingredient: the unit select is replaced by the ingredient's unit label and the amount stays
    optional. Editing the name after picking unlinks it again (back to a manual item).
  - `POST { ingredientId, amount? }`: the ingredient must exist and be visible (else 400). If an open
    (not done) item with the same `ingredient_id` exists, its amount is increased (a missing amount
    counts as 0; if both are missing it stays null) and that row is returned; otherwise a new
    ingredient-linked row is inserted. These rows behave like plan items (category group, unit from
    the ingredient, merged by a later "create from plan" merge). `amount` may be null on any item.
- Grouping and sorting happen on the client: group by category (Polish label order from
  `categories.ts`), manual items go to **Inne**, then sort by name with `Intl.Collator('pl')`. Undone
  items appear above, and the **Done** section below.
- Refresh: every 5 s `GET /api/shopping-list` and replace the list state. It's active only when
  `matchMedia('(pointer: coarse)')` matches and `document.visibilityState === 'visible'`. Pause while
  a mutation is in flight or an amount field has focus, and drop responses that started before the
  last local change. On a `visibilitychange` to visible, fetch once immediately.
- Unit display: `g` and `ml` as integers, `pcs` with up to 1 decimal.

## UI design

Approved mockups (phone, 390×844, Polish): https://claude.ai/artifact/BzKWJtaJ9xQQ8FmHx82rNb
(private to the project author). Screens: Plan (day), meal picker, cooking view, new meal, meals,
ingredients, list from plan, shopping list. This section records everything needed to build them
without opening the mockups.

**Look:** calm and light. An off-white background, white cards with a hairline border, one green
accent for actions, and a color per person. Phone-first; on wider screens the content sits in a
centered column (max ~560px) with the same bottom navigation. Light theme only for now.

**Tokens** (`src/lib/styles/base.css`, on `:root`; components use the variables, never raw hex):

| Token | Value | Use |
|---|---|---|
| `--color-bg` | `#F6F5F0` | page background, input fill |
| `--color-surface` | `#FFFFFF` | cards, header, bottom nav |
| `--color-surface-muted` | `#EFEEE7` | "Kupione" section, category tags |
| `--color-ink` | `#1D2420` | text |
| `--color-muted` | `#5E665F` | secondary text, inactive nav |
| `--color-subtle` | `#8A9089` | icons like drag handle, checkbox outline |
| `--color-border` | `#E2E1D8` | card borders |
| `--color-border-strong` | `#D5D4CA` | inputs, outline buttons |
| `--color-divider` | `#ECEBE3` | rows inside cards |
| `--color-accent` | `#2E6B45` | primary buttons, selected day/chip, active nav |
| `--color-accent-hover` | `#1F4E31` | hover/pressed |
| `--color-accent-soft` | `#EEF4EF` | "Dodaj posiłek" fill, per-portion summary |
| `--color-accent-soft-border` | `#9DB8A5` | dashed border of "Dodaj posiłek" |

Per-person colors come from `users` config (`color`, `tint`), not from tokens.
Radius: 10px (small inputs), 12px (inputs, icon buttons), 14–16px (cards), 999px (pills, chips).
Spacing scale 4/8/12/16/20/24px; page gutter 16px.
Type: Inter 400/500/600/700, self-hosted via `@fontsource/inter`. Sizes: 22px page titles, 18–19px
sub-page titles, 15–16px body and list items, 13–14px secondary, 11–12px labels. Uppercase
section labels: 12–13px, weight 700, letter-spacing 0.06em, muted color.

**Rules:**
- Touch targets at least 44×44px. Inputs use 16px text (prevents zoom on iOS).
- Icons: inline stroke SVG components (24px grid, stroke 2) in `src/lib/components/icons/`. No emoji, no icon font.
- Accessible markup: real `<button>`, `<a>`, `<label>`; `aria-label` on icon-only buttons; `aria-pressed` on toggles.
- Bottom navigation with four tabs: Plan, Posiłki, Składniki, Zakupy. Sub-pages (forms, cooking view,
  list from plan) have a header with a back arrow instead of a page title.

**Screen notes** (behavior visible in the mockups):
- *Plan:* the header has month and year, previous/next week arrows and a **Dziś** pill. The week bar is a
  7-column grid: weekday abbreviation, day number and a dot when the day has meals. The selected day is
  filled green. The day summary card shows a per-person table: kcal, B (białko), T (tłuszcz),
  W (węglowodany). Each meal card has a drag handle, a photo thumbnail, the title (a link to the cooking
  view), the types and a "⋯" menu (Zamień, Edytuj, Usuń). Below that is one tile per person with kcal and
  macros. **Usuń** opens a confirmation dialog („Usunąć „{nazwa}” z tego dnia?", Anuluj / Usuń) before
  removing. **Tapping a tile toggles that person's exclusion**: an excluded tile is dashed, reads "nie je",
  and shows "Dotknij, aby dodać" (Tap to add).
- *Meal picker:* a bottom sheet over the plan, with a title and the date, a close button, search,
  horizontally scrolling type chips, and rows with photo, name, types and kcal per portion.
- *Cooking view* (`/plan/[planMealId]`):
  - The header has a back arrow, the meal name, the date and type, and an edit (pencil) link.
  - A table: ingredient | one column per **included** person (excluded people's columns are hidden).
    The header cells use the person's `color`, and amount cells use their `tint`. Amounts are
    recipe amount × multiplier, formatted with `formatAmount`. The footer row shows kcal per portion per person.
  - Below is the preparation text at 16px, line-height 1.6, with line breaks kept (`white-space: pre-line`).
  - If every person is excluded, show a short note instead of the table, and still show the preparation.
  - **Keep the screen on** while the page is open (Screen Wake Lock API): request on mount, request
    again when the page becomes visible, release on leave, and fail silently where unsupported.
- *New meal / edit:* the photo drop zone, name, meal type chips (multi-select), ingredient rows
  (name, amount input, unit, remove), an ingredient search with results inline, a live per-portion
  summary (kcal, białko, tłuszcz, węgl.) and a preparation textarea. **Zapisz** is in the header.
- *Meals:* a two-column card grid (photo, name, types and kcal), search and type chips; **Nowy** in the header.
- *Ingredients:* one card list; each row has name, macros, kcal per unit and a category tag.
- *List from plan:* a card per day with a day checkbox and meal checkboxes. Unticked meals are struck
  through, and a skipped day collapses. A sticky footer shows the count and **Utwórz listę zakupów**.
- *Shopping list:*
  - **Z planu** is in the header, with a quick-add row (name, amount, unit, +) below it. The name field
    shows a dropdown of matching ingredients (name, category, unit) while typing.
  - Groups have uppercase labels, and each item row has a large tick box, the name and an amount pill (tap to edit).
    An item without an amount shows a muted "+ ilość" pill instead; tapping it opens the same inline
    amount input. The unit never changes (ingredient's unit, or the manual item's unit, or none).
  - The **Kupione (n)** section sits on the muted background, with ticked boxes and struck-through names.

## Photos

- Upload with `<input type="file" accept="image/*">`, max 10 MB. `sharp` auto-rotates from EXIF,
  resizes to max 800 px on the longer side, converts to WebP at quality ~75, and strips metadata.
  Originals aren't kept.
- Files are saved as `PHOTOS_DIR/<uuid>.webp` and served by `/photos/[file]` with
  `Cache-Control: public, max-age=31536000, immutable`. The file name is validated against
  `^[0-9a-f-]{36}\.webp$`. Optionally nginx can serve `PHOTOS_DIR` directly.
- Replacing a meal's photo writes a new file. Old files are not deleted on the spot because planned
  copies and "save as new recipe" may share them. The daily cleanup removes orphaned files.

## Auth

- `APP_PASSWORD` env var. The `/login` action compares it with `crypto.timingSafeEqual` on SHA-256
  hashes of both values.
- The session is a stateless signed cookie: an HMAC-SHA256 with `SESSION_SECRET` over the expiry
  timestamp. It's `httpOnly`, `secure`, `sameSite=lax` and lasts 180 days. Changing `SESSION_SECRET`
  logs everyone out.
- `hooks.server.ts` `handle` redirects every request without a valid cookie to `/login`, except
  `/login` itself, and returns 401 for `/api/*`.
- Login throttling: an in-memory limit of 5 failed attempts per IP per 15 minutes. The IP comes from
  `event.getClientAddress()`; behind the reverse proxy the server must set adapter-node's
  `ADDRESS_HEADER` (see the deployment note under CI/CD).

## Daily cleanup

`src/lib/server/cleanup.ts`, started from the `init` export in `hooks.server.ts`. It runs once at
startup and then every 24 h (`setInterval`):

1. Delete `plan_meals` with `date < today − 28 days` (children cascade).
2. Delete files in `PHOTOS_DIR` not referenced by `meals.photo_path` or `plan_meals.photo_path` and
   older than 1 hour (to avoid a race with an upload in progress).

This requires a single app process: PM2 `fork` mode, 1 instance.

## Environment variables

`DATABASE_URL`, `APP_PASSWORD`, `SESSION_SECRET`, `PHOTOS_DIR`, `TZ=Europe/Warsaw`, plus adapter-node's
`BODY_SIZE_LIMIT=10M` (the default of 512K would reject photos). Read them through `$env/dynamic/private`.
Commit `.env.example`, never `.env`.

## Testing

- Vitest with two projects: `node` for `src/lib/**` pure logic (nutrition, dates, shopping list
  aggregation and merge, auth cookie signing), and `browser` for components.
- Not tested now: database repositories against a real MySQL, and E2E. Business rules live in pure
  functions so that the untested database layer stays thin.

## CI/CD

Job `ci` on every push and pull request: `pnpm install --frozen-lockfile`, oxlint, `prettier --check`,
`svelte-check`, Vitest (with Playwright browsers for browser mode), `pnpm build`.

Job `deploy` after `ci`, on pushes to `master` only (GitHub environment `production`, one deploy at a
time): build, pack a release tarball (`build/`, `drizzle/`, `scripts/`, `package.json`, lockfile and
production `node_modules` installed on the runner), copy it to the VPS with `appleboy/scp-action`, then
with `appleboy/ssh-action`: unpack to `releases/<sha>`, run `scripts/migrate.js` (drizzle's mysql2
migrator; same tracking table as `drizzle-kit migrate`, so drizzle-kit is not needed on the server),
switch the `current` symlink, run the configured restart command, keep the last 5 releases. Because the
release ships its own `node_modules`, `drizzle-orm` and `mysql2` are runtime `dependencies`.

The server's `shared/.env` holds the app environment, including adapter-node's `ORIGIN` (the public URL;
without it form actions fail behind the proxy), `ADDRESS_HEADER=X-Forwarded-For` (the real client IP for
login throttling) and, if 3000 is taken, `PORT`. Secrets, variables and server requirements are listed
in `AGENTS.md` ("Deployment"). Server provisioning (nginx, TLS, the service definition) stays manual.
